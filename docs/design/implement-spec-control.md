# Контроль `implement-spec`: чтобы спека закрывалась, а не забывалась

Проблема не в том, что модель не знает девяти шагов `implement-spec` — она их читает. Проблема в
том, что через 40 сообщений и два сжатия **никто не помнит, что спека открыта**: у фазы нет объекта,
к которому можно вернуться, у неё нет конца, который проверяется без доверия модели, и нет силы,
которая вернёт её на рельсы после того, как ход закончился «сам собой».

Наблюдение, из которого всё выросло: в длинной сессии скилл отклонялся на другие задачи, спеку не
доделывал, и возвращать его приходилось вручную.

## 1. Что именно ломается в текущем коде

| Симптом | Механизм | Место |
| --- | --- | --- |
| Нечего помнить: фаза — это имя скилла, у неё нет спеки | `GuardState = { phase, gatesPassed }` | `extensions/skill-guard/engine.ts:6-11` |
| Выход из `implement-spec` не проверяется вообще | у контракта нет `gate` | `contracts.ts:99-103` |
| «Все тикеты закрыты?» спрашивать не у кого и нечем | гейты только `user`; `command`/`artifact`/`visited` из проекта не реализованы | `contracts.ts:26-31`, `docs/design/pi-matt-x.md:62-70` |
| После `/reload`, резюма или новой сессии охраны нет | состояние живёт в памяти | `index.ts:12` |
| После сжатия модель не видит открытую фазу | хука `context` нет; виден только `setStatus` | `index.ts:32-42` |
| Девять шагов делают сабагенты, а они не ограничены | обработки `PI_SUBAGENT_CHILD` в коде нет, хотя она описана | `index.ts` (нет), `docs/design/pi-matt-x.md:121` |
| Дрейф ничем не встречается: `implement-spec` даёт `bash` | `needsPermission` при `bash` возвращает `false` для любого инструмента | `engine.ts:81-86` |
| Модель закончила ход на середине — и это конец | никто не просит продолжения | `index.ts` (нет), «Не в v1» `docs/design/pi-matt-x.md:159` |

## 2. Чем это закрывает goal-x

goal-x держит длинную задачу пятью вещами, и все пять переносимы:

1. **Объект, названный до начала работы.** Цель нельзя «начать» — её создают с objective и списком
   шагов (`create_goal`), и без объектива нет фокуса.
2. **Ledger на диске.** `.pi/goals/goal_events.jsonl` + чекпоинт: что сделано, вердикт аудитора,
   статус. Живёт вне контекста, поэтому сжатие его не трогает (`docs/research/pi-goal-x.md:281-344`).
3. **Продолжение вместо тишины.** В `agent_end` взводится `continuationAfterSettleFor = goal.id`
   (`extensions/goal-events.ts:564`), в `agent_settled` вызывается `scheduler.settled()` (`:613`), а само
   сообщение отправляется через `pi.sendMessage(…, { triggerTurn: true, deliverAs: "followUp" })`
   (`goal-runtime.ts:143` → `goal-state.ts:290`). Граничный `agent_before_settle` goal-x **не
   использует вовсе** — это важно: у `continue: true` есть своя валидация (M3).
4. **Ledger в промпте.** Блок вставляется заново, поэтому переживает компакцию
   (`goal-auditor.ts`, `goal-ledger.ts`).
5. **Владение сессией и резюм.** `/goal-resume` переписывает `scheduler.owner` на текущую сессию
   (`goal-scheduler.ts:133`), `isDelegatedGoalSession` не даёт сабагенту двигать чужую цель
   (`goal-session-safety.ts:9-12`).

Подробно с строками — [`docs/research/implement-spec-control.md`](../research/implement-spec-control.md).

Пункт 3 был отвергнут для этого расширения с формулировкой «модель заканчивает ход, когда задаёт
вопрос, — гейт всё равно не откроется без человека» (`docs/design/pi-matt-x.md:159`). Для
**человеческих** гейтов это верно. Наблюдаемый сбой другой: модель заканчивает ход **не спросив
ничего** — просто уходит на другую задачу. Поэтому продолжение нужно не как замена гейта, а как
сигнал «работа не закрыта» на фазах с механическими условиями.

## 3. Предложение: пять изменений

Все пять — правки в существующих трёх файлах (`contracts.ts`, `engine.ts`, `index.ts`) плюс тесты.
Новых зависимостей нет, новых инструментов для модели нет.

### M1. Якорь спеки: фаза без неё не открывается

`implement-spec` — единственный скилл, у которого есть внешний объект. Вход требует его назвать:
issue-номер спеки (`#42`) либо путь к `.scratch/<feature>/`. Один `ui.editor` в момент входа —
тот же механизм, что уже спрашивает гейты при выходе; ответ пишется в `state.spec`.

```ts
interface GuardState {
  phase: string | null;
  gatesPassed: string[];
  spec?: { ref: string };  // M1
}
```

Почему это главное: без `spec` невозможно ни проверить закрытие (M2), ни напомнить, что открыто
(M4). Дальше якорь становится частью блокировки: `write`/`bash` в `implement-spec` без `spec` —
блок с текстом «назови спеку».

### M2. Тикет-леджер и выход только по команде

Гейт перестаёт быть только вопросом человеку и становится тегированным объединением:

```ts
type Gate =
  | { kind: "user"; quote: string; question: string; source?: string }
  | { kind: "command"; must: string; hint: string };   // regexp по выводу, isError=false
```

`command`-гейт закрывается не ответом, а **результатом инструмента**: расширение смотрит
`tool_result` от инструмента с грантом `bash`, требует `isError === false` и совпадения вывода с
`must`. Подделать нельзя — вывод приходит из раннера, а не из текста модели.

Команду проверки модель не диктует: она выводится из якоря (`#42` → `gh issue view 42 --json state -q .state`) и показывается в тексте блокировки. Поэтому `must` терпит оба натуральных ответа трекера: строку `0` (открытых под-тикетов нет) и `CLOSED`.

### M3. Продолжение на границе

Событие с правом продолжения — `agent_before_settle` (`BoundaryResult`, `types.d.ts:784,1210`);
`agent_settled` возвращает только `void` и для этого не годится (`types.d.ts:787,1211`).

У `continue: true` есть неочевидная валидация: `_buildBoundaryContext()`
(`dist/core/agent-session.js:597`) отказывает в продолжении, если последнее сообщение в контексте
имеет роль `assistant` и расширение не добавило исполнимого контекста — ошибка
`"<boundary> requested continuation without runnable model context"`. Значит форма всегда такая:

```ts
return {
  continue: true,
  entries: [{ type: "custom_message", customType: "skill-guard", content: block, display: false }],
};
```

Альтернатива, которой пользуется сам goal-x и которая обходит эту валидацию, —
`pi.sendMessage({ customType: "skill-guard", content: block, display: false },
{ triggerTurn: true, deliverAs: "followUp" })` (`types.d.ts:330,1258`). Выбирать между ними стоит
после живой проверки; в тестах чистых функций разницы нет.

Правило, при котором продолжение запрашивается (`index.ts`, `agent_before_settle`):

- у открытой фазы есть незакрытый `command`-гейт (человеческий гейт не перебиваем — там модель ждёт ответа, а не застряла);
- нет очереди входящих сообщений (`ctx.hasPendingMessages()`);
- счётчик автопродолжений на один пользовательский ход меньше потолка (`MAX_CONTINUES = 3`, сброс на `input`).

Форма — `{ continue: true, entries: [{ type: "custom_message", … }] }`; альтернатива через
`pi.sendMessage(…, { triggerTurn: true })` не понадобилась.

### M4. Блок фазы в разговоре, а не только в статусной строке

`setStatus` (`index.ts:32-42`) модель не видит. Нужно сообщение в транскрипте:

```text
[skill-guard] фаза: implement-spec · спека: #42
осталось: 3 открытых тикетов
гейт открыт: прогони проверку спеки (gh: открытые под-тикеты → 0, или state → CLOSED) — gh issue view 42 --json state -q .state
следующий шаг: tdd | code-review | diagnosing-bugs | retro | pr | handoff
```

Текст собирает чистая функция `phaseBlock()` (`engine.ts`), «осталось» берётся из последнего
ответа трекера, который расширение видело в `tool_result` (`state.tickets`), — своего запроса к
`gh` на каждый ход расширение не делает.

Пережить сжатие гарантированно может только пересборка: `custom_message`, попавший за
`firstKeptEntryId`, схлопывается вместе с историей. Поэтому блок собирается в хуке `context`
(`types.d.ts:672,1200`, транскрипт без system prompt) заново на каждый запрос — так делает и goal-x
через `context_with_system` (`goal-events.ts:84`), удерживая живой хвост (`LiveTailRetention`),
чтобы не переплачивать за префикс. Плюс пересборка на `session_compact` для случая, когда
следующий ход должен знать, что история только что сжалась.

`custom` для этого не годится — не попадает в LLM-контекст вовсе (`agent-session.js:512`).

### M5. Состояние на диске, `/matt` и наследование сабагентами

- `.pi/skills-guard/sessions/<sessionId>.json`, запись temp+rename (`docs/design/pi-matt-x.md:78-90`).
  Снимает `shortcut:` в `index.ts:12`: `/reload` и резюм больше не обнуляют охрану.
- `/matt` — статус (фаза, спека, остаток тикетов), `/matt goto <skill>` — возврат руками одной
  командой. Это и есть «ручной возврат», который сейчас делается вслепую.
- `PI_SUBAGENT_CHILD=1` → читаем файл родителя по `PI_SUBAGENT_PARENT_SESSION`, применяем те же
  grant'ы, но фазу и гейты менять нельзя. Доступа к памяти родителя у ребёнка нет — только файлы,
  канал `contact_supervisor` и финальный результат. Фабрики расширений в дочерней сессии
  выполняются заново, поэтому без этого обработчика каждый implementer/merger-сабагент стартует
  `phase = null`, то есть вообще без ограничений — а девять шагов делают именно они.

## 4. Что сознательно не делаем

- **Аудитор на второй модели** — деньги и доверие к чужому суждению. Механические гейты дешевле и
  проверяемы.
- **Фаза на каждый тикет** — состояние станет вектором тикетов, а `contracts.ts` перестанет быть
  таблицей. Ledger + `command`-гейт дают то же без этого.
- **Квиз по тикетам человеку** — вопрос «все тикеты закрыты?» заменяется запросом к трекеру:
  человек не обязан помнить, что открыто.
- **Запрет `subagent`/`workflow` в фазе** — они там нужны по делу. Дрейф ловится не запретом
  инструмента, а продолжением: уйти молча нельзя, а закончить ход с открытыми тикетами — нельзя.

## 5. Порядок и проверки

Сделано: **M1** (якорь) → **M5** (диск + `/matt`) → **M2** (`command`-гейт) → **M4** (блок) →
**M3** (продолжение). Осталось: наследование сабагентами.

**Реализовано иначе, чем задумано:** вариант `artifact` не появился (ничего его не использует — YAGNI),
а `spec.check` не поле состояния: команда выводится из якоря (`specCheck()` в `engine.ts`).

1. **M1** (якорь) — `engine.ts`: поле `spec`, гейт входа; тест: `decide(at("implement-spec"), tool("write"))` без `spec` → блок, со `spec` → allow.
2. **M4** (блок) — `index.ts`: сборка строки, хук `context`; тест на текст.
3. **M5** (диск + `/matt`) — `state.ts` новый модуль, 20 строк; тест: запись/чтение/битый файл.
4. **M3** (продолжение) — `index.ts`: `agent_before_settle`; тесты: продолжение при открытом `command`-гейте, тишина при открытом `user`-гейте, потолок срабатывает.
5. **M2** (`command`-гейт) — `engine.ts` + `contracts.ts`; тест: `tool_result` с кодом 1 гейт не закрывает, с кодом 0 — закрывает.
6. **Наследование сабагентов** — последним: без живой проверки риск выше всего.

`node --test`, чистые функции без Pi; живая проверка — по скиллу `verify-pi-package-via-rpc`, иначе
повторится история «тесты зелёные, в живой сессии не проверяли».

Отдельно проверить на живой сессии то, что нельзя проверить тестом: проходит ли `continue: true`
с `custom_message`, и переживает ли блок сжатие (дважды нажать compact и убедиться, что фаза и
остаток тикетов всё ещё видны).

## 6. Риски
- **Продолжение может спорить с человеком.** Если модель закончила ход, ожидая ответа, которого нет
  в `state`, `continue` её подтолкнёт. Смягчение: продолжение только при закрытом человеческом гейте
  и с потолком.
- **Трекер может быть недоступен** (`gh` не авторизован, сеть). Тогда `command`-гейт не закрывается
  никогда, и фаза не выходит. Нужен явный обход: `/matt override` с причиной — механизм в проекте
  уже есть (`GLOSSARY.md`, «Обход»).
- **`context` и кеш.** Блок маленький, но вставляется в хвост на каждый запрос; при частых
  продолжениях это пере-pay промпта на каждом ходу. Мера — держать его коротким и неизменным
  внутри шага, чтобы менялся только хвост.
- **Точный endpoint frontier'а не проверен** (`gh` sub-issues); пока не подтверждён — гейт
  настраивается на любую команду, которая возвращает 0 при закрытой спеке.

## 7. Что проверено, а что нет

Проверено вживую (реальная сессия Pi через RPC, код из рабочей копии):

- `/matt goto implement-spec` и `/matt spec #42` → `disposition: "handled"`, на диске
  `.pi/skills-guard/sessions/<id>.json` = `{"phase":"implement-spec","spec":{"ref":"#42"},"gatesPassed":[]}`.
- Перезапуск процесса на том же файле сессии (= `/reload`) → `/matt` сообщает ту же фазу и спеку,
  статус-строка: `phase: implement-spec → tdd | code-review | …`.
- Блок фазы реально доходит до модели: в четырёх разных ходах она цитировала из него и готовую
  команду проверки спеки (`gh issue view 42 --json state -q .state`), и строку про открытый гейт.
- `npx tsc --noEmit` — 0; `npm test` — 64/64.

Не проверено вживую:

- **Два настоящих `/compact`**: Pi отказывается сжимать маленькую сессию
  (`Nothing to compact (session too small)`), а набить контекст до порога в тесте — это уже
  полноценный длинный разговор. Механизм держится на том, что `context` вызывается на каждый
  запрос к уже пересобранным сообщениям (тест: ровно одно сообщение, тот же текст).
- Выход из фазы при открытых тикетах и автопродолжение — только юнит-тесты, без живой модели.
- `/reload` — проверен как перезапуск процесса на том же файле сессии, а не нажатием в TUI.

Замечено вживую: если ссылка на спеку не резолвится (`#42` нет в репозитории), проверка спеки
падает, гейт остаётся открытым и модель на каждом ходу говорит про гейт, а не про задачу. Это
честное поведение («проверка не прошла»), но шумное; лечится реальной ссылкой на спеку.
