# pi-flow-guard: расширение, удерживающее модель внутри флоу mattpocock

Статус: **устарело.** Заменено на [pi-matt-x.md](pi-matt-x.md) после гриля: аудитор, YAML-объявление флоу, `setActiveTools` и автопродолжение из дизайна убраны, фаза привязана к загрузке скилла. Ничего не реализовано.

Основания: API расширений Pi 1.4.0 (`docs/extensions.md`) и паттерны из `pi-goal-x@0.34.1`.
Критерии этапов по скиллам — в `docs/research/mattpocock-flow.md`.

---

## 1. Почему скиллы не держат

Набор mattpocock — это **текст**. `grilling/SKILL.md:28` говорит «Do not act on it until the user
confirms you have reached a shared understanding», `implement-spec/SKILL.md:1-40` перечисляет 9 шагов.
Ни одно из этих требований не проверяется кодом. Всё держится на послушности модели в момент, когда
у неё в контексте 30+ сообщений, сжатие уже выкинуло середину инструкции, а инструменты для действия
доступны прямо сейчас.

Отсюда наблюдаемые проскоки:

| Проскок | Почему возможен |
|---|---|
| grilling → сразу начал делать | `write`/`edit` доступны в любой момент; «дождись подтверждения» — только фраза |
| to-spec → спека без допроса | нет проверки, что grilling-раунды вообще были |
| to-tickets → реализация без тикетов | нечего проверять: тикетов нет, но `write` работает |
| implement-spec → пропущен `tdd`/ветка/worktree | `implement-spec/SKILL.md:4-5` — подпункты, не гейты |
| пропущен финальный `code-review` | шаг 7 из 9, к концу контекст сжат |
| triage → взял в работу без `ready-for-agent` | метка живёт в GitHub, а не в состоянии агента |

Вывод: **инструкция должна остаться инструкцией, а принуждение — стать состоянием процесса,
которое живёт в расширении, а не в контексте модели.**

## 2. Что даёт Pi, чтобы это сделать механически

Всё ниже — реальные хуки `pi.on()` (`docs/extensions.md:94-125, 147-165`).

| Механизм | Хук / API | Что даёт | Слой |
|---|---|---|---|
| Подмена/обогащение ввода пользователя | `input` | поймать «загриль меня про X» и **включить флоу до того, как модель начала думать** | L1 |
| Стабильный блок состояния в каждом запросе | `context` (+ `context_with_system`) | правила текущего этапа никогда не выпадают из контекста | L1 |
| Смена активных инструментов | `pi.setActiveTools()` | в фазе допроса модель **не видит** `write`/`edit`/`bash` | L2 |
| Жёсткий блок вызова | `tool_call` → `{ block: true, reason }` | страховка к L2 + обучающий `reason` вместо стены | L2 |
| Запрет перехода без критериев | собственный инструмент `flow_advance` | переход делает только расширение, проверив артефакты | L3 |
| Независимая приёмка этапа | `ctx.modelRegistry.streamSimple()` / субагент | аудитор читает артефакт и возвращает pass/fail | L4 |
| Продолжение цикла без пользователя | `agent_settled` → `{ continue: true }` | этап не бросается на середине; но на человеческом гейте — стоп | L5 |
| Устойчивость кэша промпта | `before_provider_request` + сдвиг breakpoint | блок флоу не убивает кэш префикса | — |
| Изоляция сабагентов | `PI_SUBAGENT_CHILD` / `PI_SUBAGENT_DEPTH` | дочерний агент не может протолкнуть этап | — |

Критично: `agent_end` — **не** сигнал покоя (там ещё ретраи, компакция, очередь). Единственная
точка, где Pi гарантирует отсутствие автоматической работы — `agent_settled`
(`docs/extensions.md:158-161`). goal-x это соблюдает: продолжение взводится в `agent_end`
(`extensions/goal-events.ts:558`), а планируется только в `agent_settled`
(`extensions/goal-events.ts:614`).

## 3. Пять слоёв принуждения

Слои вложенные: каждый следующий ловит то, что проскочило предыдущий. Дёшево — L1, дорого — L4.

### L1 — присутствие правил (soft, бесплатно)

В каждый запрос через `context` добавляется request-only блок, **не** попадающий в историю:

```
[FLOW mattpocock stage=grill round=2/∞ goalId=…]
Разрешено: read, grep, find, ls, ask_user_question, flow_advance
Запрещено: write, edit, bash, commit  → блокируются кодом, не просьбой
Критерий выхода этапа:
  ⬜ нет открытых вопросов фронтьера
  ⬜ пользователь подтвердил общее понимание
Ссылка: ~/.pi/agent/skills/grilling/SKILL.md
```

Блок состоит из двух частей, как в goal-x: **стабильный** `state` (этап, правила, чеклист) и
**волатильный** `counters` (раунд, токены, время). Разделение — не косметика: стабильная часть
не меняется между ходами и держит префикс, волатильная растёт медленно
(`extensions/goal-events.ts:456-556`, `LiveTailRetention` в `goal-live-retention.ts`).

### L2 — у инструментов нет варианта «просто сделать» (hard)

Два независимых механизма, оба нужны:

1. `pi.setActiveTools([...])` при входе в этап — набор объявленных модели инструментов урезается.
   Модель не видит `write` в допросе, значит не строит план «сейчас запишу».
2. `pi.on("tool_call", …)` возвращает `{ block: true, reason }` для всего, что вне allowlist —
   страховка на случай активированных позже инструментов, MCP, codemode, вложенных вызовов
   (`ctx.executeTool` тоже проходит через `tool_call`, `docs/extensions.md:261`).

`reason` пишется как **инструкция, а не отказ**: `«write заблокирован: этап grill не завершён
(открыт 1 вопрос). Задай следующий раунд через ask_user_question или вызови flow_advance.»`
Это то же, что делает goal-x (`extensions/goal-events.ts:133-186`).

Fail-closed: падение обработчика `tool_call` блокирует инструмент
(`docs/extensions.md:375`) — нужное поведение по умолчанию.

### L3 — переход только через критерии

Модель не может «решить», что этап закончен. Единственный путь — инструмент `flow_advance`,
который:

- сверяет exit criteria из объявления флоу;
- при невыполнении возвращает `isError: true` и **список недостающего** (не «нельзя», а «не хватает
  вот этого»);
- при выполнении пишет событие в ledger, меняет этап, пересобирает active tools и инжектит
  новый блок.

Именно так goal-x поступает с `update_goal({status:"complete"})`: сначала аудитор, потом архив
(`extensions/goal-completion.ts`, `goal-auditor.ts`).

### L4 — независимый аудитор там, где критерий — суждение

Часть критериев не проверяется файлом: «спека полная», «код-ревью действительно сделано»,
«вопросы были по делу». Для них — отдельный read-only прогон:

- отдельная сессия через `ctx.modelRegistry.streamSimple()` или субагент с урезанным набором
  инструментов (только чтение);
- на вход — артефакт (файл спеки, диф, отчёт ревью) и рубрика из объявления флоу;
- на выход — `pass | warn | fail` + причины; вердикт попадает в ledger и в L1-блок как
  `[AUDITOR REJECTION]`.

Прямой аналог — `goal-auditor.ts` + `auditor-selector.ts` (выбор модели-аудитора) и
`goal-oracle.ts` (read-only консультант при заявленном тупике).

### L5 — цикл не обрывается сам

Если у этапа есть обязательная незакрытая работа (фронтьер тикетов, красные тесты), расширение
в `agent_settled` возвращает `continue: true` и модель продолжает без «а я думал, мы закончили».

Обратное тоже важно: при **человеческом гейте** продолжение не запрашивается, а мутирующие
инструменты заблокированы — модель физически не может «проскочить» вопрос, потому что ей нечем
действовать и её никто не подгоняет.

## 4. Состояние и объявление флоу

### Состояние

```
.pi/flows/
  active.json                      # какой флоу активен в сессии (id + stage)
  <flowId>/
    flow.json                      # { id, kind, stage, round, artifacts, gate, revision }
    flow.lock                      # файловый лок на время записи
    events.jsonl                   # append-only: stage_entered, gate_blocked, gate_passed,
                                   #   artifact_checked, auditor_verdict, override
```

Переиспользовать, а не изобретать: `storage/atomic-rename.ts` (write-temp + rename),
`storage/goal-lock.ts`, `storage/goal-root.ts` из goal-x — это ровно тот же класс задачи
(несколько процессов/сессий, один файл).

Правило goal-x, которое стоит скопировать: **мутации копятся за ход в памяти и сбрасываются
одной транзакцией в конце хода под локом**; при изменившемся `revision` локальный буфер
отклоняется (`extensions/goal-service.ts:180-215`). Без этого `flow.json` будет затираться
параллельными сессиями.

### Объявление флоу — декларативно, не в коде

Пайплайн лежит в `.pi/flows/defs/mattpocock.yaml`, движок его читает. Причина: этапов ~8 и они
меняются вместе со скиллами; хардкод в TS означает пересборку расширения на каждую правку
промпта. Схема:

```yaml
id: mattpocock
stages:
  - id: grill
    skill: grilling
    allow: [read, grep, find, ls, bash, ask_user_question, flow_status, flow_advance]
    deny:  [write, edit]
    exit:
      - kind: state        # расширение само знает про открытые раунды
        check: no_open_round
      - kind: user_confirm
        prompt: "Фронтьер пуст — понимание общее, двигаемся к спеке?"
  - id: spec
    skill: to-spec
    allow: [read, grep, find, ls, write, edit, flow_status, flow_advance]
    exit:
      - kind: artifact
        path: "docs/specs/*.md"
        require_headings: [...]      # заполняется из to-spec/SKILL.md
      - kind: auditor
        rubric: spec-completeness
```

Типы критериев, которых достаточно: `state` (внутреннее состояние флоу), `artifact` (файл + разделы
+ непустота), `command` (например `gh issue list --label ready-for-agent`), `git` (ветка/коммиты),
`user_confirm`, `auditor`. Всё остальное — производное.

## 5. Что копируем из goal-x поимённо

| Паттерн | Откуда | Зачем |
|---|---|---|
| Тонкий установщик + ядро состояния | `extensions/goal.ts:1-30` (`goal.ts` только регистрирует) | одна точка входа, подсистемы в отдельных файлах |
| Транзакционный рубеж мутаций | `goal-service.ts` | единственное место записи на диск, легко тестировать |
| Request-only блок состояния | `goal-context.ts` + `goal-events.ts:456-556` | правила в контексте, но не в истории |
| Стабильный/волатильный блок | `goal-live-retention.ts` | префикс кэша не инвалидируется |
| Сдвиг cache breakpoint назад | `goal-prompt-cache.ts:1-68` | Anthropic/Bedrock не теряют кэш из-за инжекта |
| Гейт в `tool_call` с обучающим reason | `goal-events.ts:133-186` | блок вместо стены |
| Продолжение только из `agent_settled` | `goal-events.ts:558, 614` | не ломается о ретраи/компакцию |
| Ledger + вердикт аудитора в промпте | `goal-auditor.ts`, `goal-ledger.ts` | отказ аудитора не забывается после сжатия |
| `isDelegatedGoalSession` | `goal-session-safety.ts:10-12` | сабагент не управляет флоу родителя |
| Fail-closed на ошибке обработчика | `goal-events.ts:133` | безопасный дефолт |

Оценка объёма: goal-x — ~55 файлов и 0.34.x за плечами. Честный минимум для flow-guard —
**12–15 файлов**: объявление+парсер флоу, состояние, сервис-мутации, storage (3 файла можно
взять у goal-x как есть), L1-блок, L2-гейт, L3-переход, ledger, аудитор, продолжение,
команды/UI, точка входа.

## 6. Что НЕ делать

- **Не дублировать текст скиллов** в расширении. Скиллы остаются источником инструкций;
  расширение держит только *оболочку*: этап, разрешённые инструменты, критерий выхода. Иначе
  две копии правил разъедутся.
- **Не заменять систему промптов** (`systemPrompt` / `forceSystemPrompt`) — это обнуляет кэш
  префикса на каждом ходе (`docs/extensions.md:228`).
- **Не спрашивать пользователя через свою UI-панель**, пока `ask_user_question` работает:
  формат вопросов — дело скилла, а не движка. Движок проверяет только «раунд открыт/закрыт».
- **Не делать блокировку неотключаемой.** Нужен `flow_override` с обязательной причиной и записью
  в ledger: дрейф должен быть виден, а не невозможен. Иначе первая же ложная блокировка
  (например, нужно править файл во время допроса) выключает расширение навсегда.

## 7. Открытые вопросы (нужно решение до кода)

1. **Строгость.** (a) только L1 — напоминания; (b) L1–L3, жёсткая блокировка инструментов;
   (c) L1–L4 с аудитором на каждом этапе. Рекомендация: (b) для повседневной работы,
   аудитор включается только на `spec` и `review`.
2. **Как флоу включается.** (a) только явная команда `/flow start grill`; (b) авто-перехват
   во `input` по триггер-фразам скиллов; (c) модель сама вызывает `flow_start` по указанию
   из L1-блока. Рекомендация: (b) как основной путь + (a) как ручной, (c) не полагаться.
3. **Автопродолжение.** Разрешать модели крутиться внутри этапа без пользователя
   (как `autoContinue` в goal-x) или останавливаться после каждого шага? Рекомендация:
   внутри этапа — да, на человеческих гейтах — всегда стоп.
4. **Сабагенты.** Только наследуют этап (не могут двигать) — или им разрешается свой под-флоу
   (implementer → tdd)? Рекомендация: наследование read-only, как `isDelegatedGoalSession`.

## 8. Риски

- **Ложные блокировки.** Реальный кейс: во время допроса нужно поправить файл, чтобы показать
  вариант. Лечится `flow_override`, но он должен быть дешёвым.
- **Стоимость L4.** Аудитор — это отдельный прогон модели на каждый переход. На 8 этапах это
  ощутимо; отсюда рекомендация включать его точечно.
- **Кэш промпта.** Любая ошибка в стабильности L1-блока = инвалидация префикса каждый ход.
  Здесь goal-x — единственный надёжный образец, и его `LiveTailRetention` неочевиден.
- **Несколько сессий / веток.** `flow.json` пишется из нескольких процессов; без лока и
  `revision` состояние будет затираться.
- **Неинтерактивные режимы.** В `json`/`print` режимах `ctx.ui` нет; человеческий гейт должен
  деградировать в «остановиться и ждать ввода», а не зависнуть.
