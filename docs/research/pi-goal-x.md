# Исследование внутреннего устройства расширения pi-goal-x (v0.34.1)

> Настоящий документ представляет собой детальный технический разбор архитектуры и исходного кода расширения `pi-goal-x` версии 0.34.1, установленного в окружении Pi. Все утверждения основаны строго на первоисточниках: исходном коде (`extensions/`), конфигурационных файлах (`package.json`) и собственной проектной документации пакета (`docs/`).

---

## 1. Назначение и концепция: отличие от обычного TODO/планирования

`pi-goal-x` — это расширение для агентной среды Pi, реализующее **рантайм долгоживущих целей** (*long-running goal runtime*) поверх базового исполнителя (`docs/agent-flow-design.md:12`).

В отличие от стандартных списков задач (TODO) или простых систем ведения заметок, `pi-goal-x` решает комплексную проблему надежного автономного выполнения масштабных задач:
1. **Разделение ролей и владения намерением**: Пользователь единолично владеет намерением (*owns intent*); основной агент выполняет работу (*executing agent*); сторонний независимый агент проверяет факт выполнения (*independent auditor*); рантайм координирует переходы и ведет журнал транзакций (`docs/agent-flow-design.md:16-24`).
2. **Формальные контракты завершения (*Verification Contracts*)**: Цели и отдельные задачи могут иметь явные критерии приемки (`verificationContract`, `goal-record.ts:64`, `goal-contract.ts:13`). Достижение цели оценивается не по самоотчету модели, а по фактическим артефактам в файловой системе.
3. **Автономный цикл с защитой от зацикливания (*Autonomous Continuation*)**: Агент продолжает выполнение автоматически после каждого шага (`autoContinue: true`), но рантайм защищен лимитами автономных запусков (`maxAutonomousRuns`), замедлением повторных холостых шагов (`idleContinuationBackoff`, `goal-scheduler.ts:40`), распознаванием зависания (`checkStall`, `goal-state.ts:660`) и консультацией стороннего оракула при блокировке (`Blocker Oracle`, `goal-oracle.ts:1`).
4. **Двухуровневая модель состояния (Pool vs Focus)**: Проект может содержать произвольное количество открытых целей в едином пуле (`.pi/goals/active_goal_*.md`), но конкретная сессия Pi фокусируется ровно на одной цели (`focusedGoalId`). При этом переключение фокуса доступно только человеку (`docs/architecture.md:118`).
5. **Префиксная стабильность контекста (*Prompt Cache Preservation*)**: Данные цели и задачи внедряются в контекст на лету, не перезаписывая системный промпт и не ломая кэш провайдера LLM (`docs/prompt-caching.md:3`).

## 2. Режимы целей: regular, sisyphus, token budget

В расширении заложены два режима планирования и механизм жесткого бюджетного контроля (`goal-record.ts:2-6`):

### Regular (Flexible)
- Запускается через команду `/goal [seed]` или `/goal-direct <objective>` (`goal-commands.ts:200-244`).
- Представляет собой адаптивный результат (*outcome-oriented goal*): агент сам решает, как декомпозировать цель, какие задачи выделить и в каком порядке их выполнять (`docs/architecture.md:128`).
- На каждом такте модель анализирует обстановку и решает следующее конкретное действие.

### Sisyphus (Ordered)
- Запускается через команду `/sisyphus [seed]` или `/sisyphus-direct <objective>` (`goal-commands.ts:246-285`).
- Предназначен для строго упорядоченных сценариев: миграций, поэтапных рефакторингов, релизных процедур (`README.md:52`).
- **Реализация в коде**: В коде *нет* отдельного стейт-машины или счетчика шагов (`docs/architecture.md:133-134`, `docs/agentic-runtime-prd.md:65`). Различие исключительно стилистическое и промпт-ориентированное (*prompt/criteria style*):
  - При создании проверяется, что формулировка содержит явные нумерованные шаги: регулярное выражение `/\b\d{1,2}\s*[).:]|\bstep\s*\d+/i` (`goal-contract.ts:47`).
  - Промпты напоминают модели: «не спешить, не пропускать промежуточные шаги, не выдумывать preflight-действия» (`docs/architecture.md:136`, `prompts/goal-prompts.ts:180`).
  - Завершение разрешается только тогда, когда выполнены абсолютно все упорядоченные шаги.

### Token Budget (`tokenBudget`)
- Опциональный лимит расхода токенов на весь жизненный цикл цели (`goal-record.ts:56`, `goal-accounting.ts:80`).
- Задается целым положительным числом при создании цели (`create_goal`, `token_budget`) или через `/goal-tweak` (`goal-core-tools.ts:182`).
- **Принцип работы**: Не имеет отношения к объему контекстного окна. `GoalAccounting` суммирует реальные токены, затраченные агентом за все сессии работы над данной целью (`goal-accounting.ts:30-45`).
- При исчерпании лимита цель автоматически и необратимо переходит в специальный статус `budget_limited` (`goal-state.ts:630`):
  - `autoContinue` выключается;
  - В журнал заносится событие `goal_budget_limited` (`goal-ledger.ts:32`);
  - Модели однократно передается «wrap-up steering»: указание подвести итог проделанной работы, не начинать новых подзадач и не заявлять о фиктивном завершении (`goal-events.ts:518-530`). Продолжение работы возможно только после изменения бюджета пользователем через `/goal-tweak`.

## 3. Точка входа и компонентная архитектура

### Точка входа (`extensions/goal.ts`)
Файл `extensions/goal.ts` представляет собой предельно тонкий установщик (37 строк кода, `extensions/goal.ts:20-37`). Он:
1. Проверяет, не является ли текущий процесс делегированным воркером/сабагентом (`isDelegatedGoalSession()`, `goal-session-safety.ts:10`). Если да — регистрирует только контекстный фильтр и выходит, предотвращая вмешательство сабагента в управление целью родителя.
2. Регистрирует кастомные рендереры сообщений в TUI Pi: `GOAL_EVENT_ENTRY` и `GOAL_AUDIT_ENTRY` (`goal-format.ts:20-25`).
3. Создает общее ядро `const core = createGoalCore(pi, dependencies)` (`goal-state.ts:166`).
4. Вызывает установщики специализированных подсистем:
   - `registerGoalCommands(core)` (`goal-commands.ts:98`)
   - `registerGoalTools(core)` (`goal-tools.ts:14`)
   - `registerGoalEvents(core)` (`goal-events.ts:60`)

## 4. Модель состояния и персистентность

Хранение состояния в `pi-goal-x` строго разделено на три уровня: файлы целей, глобальный журнал событий и сессионные записи Pi (`docs/architecture.md:52-87`).

### 1. Файлы целей (`storage/goal-files.ts`, `storage/goal-root.ts`)
- **Расположение**: По умолчанию каталог `.pi/goals/` в корне рабочей директории. Путь может быть переопределен глобально или в проекте через ключ `goalsRoot` или переменную `PI_GOAL_ROOT` (`storage/goal-root.ts:16-30`).
- **Именование файлов**:
  - Активные: `.pi/goals/active_goal_<timestamp>_<id>.md` (`storage/goal-files.ts:285`).
  - Архивные: `.pi/goals/archived/goal_<timestamp>_<id>.md` (`storage/goal-files.ts:289`).
- **Гибридный формат файла** (`storage/goal-files.ts:365-385`):
  Файл начинается с валидного JSON-блока с метаданными (версия 3), за которым следует структурированный Markdown, предназначенный для чтения и прямого редактирования человеком:
  ```markdown
  {
    "version": 3,
    "id": "g-abc123",
    "objective": "...",
    "status": "active",
    "revision": 4,
    ...
  }

  # Goal Prompt

  <Текст цели, редактируемый пользователем>

  ## Progress
  - Status: in progress
  - Tokens used: 14.2K
  ...

  ## Tasks
  <!-- blockCompletion: false -->
  - [x] task-1: Setup database
  - [ ] task-2: Write API endpoints
  ```
- **Синхронизация правок пользователя**: При каждом обращении рантайм вызывает `mergeGoalPromptFromDisk` (`storage/goal-files.ts:560`). Если пользователь вручную отредактировал текст под заголовком `# Goal Prompt`, функция `extractObjectiveFromBody` извлекает новый текст и обновляет цель в памяти.

### 2. Блокировки и атомарность записи (`storage/goal-lock.ts`, `storage/atomic-rename.ts`)
- **Межпроцессная блокировка**: Для предотвращения гонок между несколькими сессиями или процессами перед записью создается эксклюзивный lock-файл `.pi/goals/.locks/<goalId>.lock` с флагом `wx` (`storage/goal-lock.ts:55-80`).
  - Записывается payload `{ pid, startedAt }`.
  - Защита от зависших блокировок: если возраст lock-файла превышает TTL (30 секунд) или процесс с указанным `pid` мертв (`process.kill(pid, 0)`), блокировка признается устаревшей и принудительно снимается (`storage/goal-lock.ts:85-98`).
  - Ожидание блокировки синхронное и короткое: через `Atomics.wait(SharedArrayBuffer)` (до 8 попыток по 1 мс, `storage/goal-lock.ts:35-40`).
- **Атомарная замена файлов**: Запись файлов идет через уникальный временный файл (`.tmp`) с последующим переименованием (`storage/goal-files.ts:205-225`).
  - Модуль `atomic-rename.ts` учитывает особенности Windows: при возникновении транзитных ошибок файловой системы (`EPERM`, `EACCES`, `EBUSY`, возникающих из-за сканеров или удерживаемых дескрипторов) выполняется повтор с экспоненциальной задержкой (`storage/atomic-rename.ts:30-50`).

### 3. Структура данных `GoalRecord` (`goal-record.ts:29-65`)
```ts
interface GoalRecord {
  id: string;                          // Уникальный идентификатор
  objective: string;                   // Полная формулировка цели
  status: GoalStatus;                  // "active" | "paused" | "blocked" | "budget_limited" | "complete"
  autoContinue: boolean;               // Флаг автоматического продолжения
  usage: GoalUsage;                    // { tokensUsed: number, activeSeconds: number }
  sisyphus: boolean;                   // Флаг упорядоченного режима
  createdAt: string;                   // ISO timestamp
  updatedAt: string;                   // ISO timestamp
  activePath?: string;                 // Относительный путь к активному файлу
  archivedPath?: string;               // Путь к архивному файлу
  stopReason?: "user" | "agent";       // Кто остановил цель
  pauseReason?: string;                // Причина блокировки/паузы
  pauseSuggestedAction?: string;       // Рекомендация агента пользователю
  skipAuditor?: boolean;               // Флаг отключения аудитора для этой цели
  revision?: number;                   // Монотонный счетчик мутаций (для optimistic concurrency)
  tokenBudget?: number;                // Лимит токенов
  scheduler?: GoalSchedulerState;      // Состояние планировщика (waiting, checks, runs)
  currentTaskId?: string;              // Идентификатор задачи в фокусе исполнения
  taskList?: GoalTaskList;             // Дерево задач { tasks, blockCompletion, proposedAt }
  verificationContract?: string;       // Текст контракта верификации
}
```

### 4. Структура задачи `GoalTask` (`goal-record.ts:10-21`)
```ts
interface GoalTask {
  id: string;                          // Короткий slug (например, "t1")
  title: string;                       // Название задачи
  status: "pending" | "complete" | "skipped";
  completedAt?: string;
  skippedAt?: string;
  evidence?: string;                   // Доказательство выполнения (обязательно при контракте)
  skipReason?: string;                 // Обязательная причина пропуска
  verificationContract?: string;       // Контракт на уровне задачи
  lightweightSubtasks?: boolean;       // Подзадачи не блокируют завершение родителя
  subtasks?: GoalTask[];               // Рекурсивное поддерево
}
```

### 5. Журнал событий `GoalLedger` (`goal-ledger.ts:11-55`)
Единый append-only JSONL файл на проект: `.pi/goals/goal_events.jsonl`. Содержит 29 типов событий: от создания и смены фокуса до детальных шагов аудита и результатов Blocker Oracle. Журнал никогда не перезаписывается. При сбоях аппенда основная транзакция записи цели не откатывается, а регистрируется предупреждение через `onDiagnostic` (`goal-service.ts:55`).

### 6. Сессионный фокус (`GoalFocusEntry`)
Фокус сессии сохраняется через служебную запись Pi `pi.appendEntry("pi-goal-focus", { version: 1, focusedGoalId, reason })` (`goal-state.ts:470`). Это гарантирует, что фокус привязан к конкретной ветке истории сессии, не попадает в контекст модели и не конфликтует с параллельными сессиями.

## 5. Инструменты модели (Tools Surface)

Список инструментов в `pi-goal-x` строго разграничен между обычным ходом работы и процессом составления черновика (`goal-tool-names.ts:10-35`).

### Рабочие инструменты (Execution Profile)

В режиме обычного выполнения модель получает фиксированный набор из 3 или 5 инструментов в зависимости от настройки `disableTasks` (`goal-tool-names.ts:16-22`):

#### 1. `get_goal` (`goal-core-tools.ts:48-165`)
- **Назначение**: Чтение состояния сфокусированной цели.
- **Параметры**:
  - `section` (optional): `"summary" | "objective" | "tasks" | "history"` (по умолчанию `"summary"` — компактный обзор).
  - `task_id` (optional): идентификатор конкретной задачи (только при `section="tasks"`).
  - `cursor` (optional): base64url-токен для постраничной загрузки больших разделов (порциями по 4000 символов, `goal-detail.ts:5`).
  - `verbose` (optional boolean): вывод полного детального отчета со всеми метаданными.
  - `include_history` (optional boolean): включение последних событий из журнала.

#### 2. `create_goal` (`goal-core-tools.ts:175-230`)
- **Назначение**: Создание и установка фокуса на новую цель. Разрешен к вызову *только* при явном распоряжении пользователя.
- **Параметры**:
  - `objective` (string, required): полный текст цели с критериями.
  - `mode` (optional): `"regular" | "sisyphus"`.
  - `token_budget` (optional integer >= 1): лимит токенов.

#### 3. `update_goal` (`goal-core-tools.ts:240-520`, `goal-tool-inputs.ts:37-80`)
- **Назначение**: Фиксация терминальных исходов или объявление ожидания продолжения.
- **Параметры**:
  - `status` (optional): `"complete" | "blocked" | "paused"`.
  - `reason` (optional string): обязателен для `blocked` (конкретная причина тупика) и `paused`.
  - `attempted_actions` (optional array of strings): список предпринятых действий до блокировки (до 8 элементов по 240 символов).
  - `suggested_action` (optional string): рекомендация пользователю при паузе.
  - `completion_summary` (optional string): резюме завершения (рассматривается аудитором как *недоверенное утверждение*).
  - `continuation` (optional object):
    - `{ kind: "ready" }` — готовность к продолжению;
    - `{ kind: "wait", reason, deadline, wait_id?, polling?: { interval_seconds, max_checks } }` — переход в режим ожидания таймера или внешнего события (требует `strictExecutionContract: true`).

#### 4. `set_goal_tasks` (`goal-task-tools.ts:248-380`)
- **Назначение**: Первичное создание или полная структурная замена дерева задач. **Всегда запрашивает интерактивное подтверждение пользователя через диалоговое окно** (`goal-task-confirmation.ts:10`).
- **Параметры**:
  - `tasks`: плоский массив задач с указанием связей `{ id, title, parent_id?, verification_contract?, lightweight_subtasks? }` (максимум 50 задач, глубина ограничена `subtaskDepth`).
  - `block_completion` (optional boolean): блокировать ли завершение цели при наличии невыполненных задач.
  - `change_summary` (optional string): описание изменений.

#### 5. `update_goal_task` (`goal-task-tools.ts:410-580`, `goal-tool-inputs.ts:3-35`)
- **Назначение**: Изменение статуса задачи без остановки хода агента.
- **Параметры**:
  - `task_id` (string): ID задачи.
  - `status`: `"start"` (берет задачу в фокус исполнения `currentTaskId`) | `"complete"` | `"skipped"` | `"pending"` (повторное открытие пропущенной задачи; завершенные задачи открывать повторно запрещено).
  - `evidence` (optional string): доказательство выполнения (строго обязательно, если у задачи есть `verificationContract` и не включен `disableContracts`).
  - `reason` (optional string): обязательная причина при статусе `skipped`.
  - `updates` (optional array): пакетное обновление задач (от 1 до 100 элементов).

### Инструменты стадии черновика (Drafting Profile)

Когда пользователь вводит команду `/goal`, `/sisyphus` или `/goal-tweak`, расширение временно подменяет рабочий профиль инструментов на специальный черновой профиль (`goal-drafting.ts:230-340`, `goal-tool-names.ts:24-28`):

6. `goal_question`: Задает пользователю один структурированный вопрос с вариантами ответов (`question`, `options`, `recommended`, `allow_custom`).
7. `goal_questionnaire`: Задает серию связанных уточняющих вопросов в едином TUI-диалоге (`questions: [{ id, question, context, options, recommended, allow_custom }]`).
8. `propose_goal_draft`: Показывает пользователю финальное модальное окно с предложением цели и структуры задач. Пользователь может нажать «Confirm» (атомарно создает/обновляет цель и переводит сессию в рабочий режим) или «Continue Chatting» (оставляет черновик открытым для доработки).

## 6. Управление контекстом и Prompt Caching

Взаимодействие расширения с контекстом LLM организовано через событие Pi `context_with_system` (`goal-context.ts:5`, `goal-events.ts:88-116`). Это решает задачу предоставления модели актуального состояния без загрязнения истории и без срыва аппаратного кэша провайдеров (`docs/prompt-caching.md:1-40`).

### Механизм внедрения блока цели (*Injected Goal Block*)
Информация о цели **не сохраняется** как обычные пользовательские сообщения в истории сессии. Вместо этого при формировании каждого запроса функция `currentGoalContextParts` (`goal-events.ts:456`) синтезирует динамический блок, разделенный на две части:
1. **Стабильная политика (`state` / policy)**: Текст цели, правила работы с инструментами, дерево задач с контрактами, замечания предыдущего отклонения аудитором (`[AUDITOR REJECTION]`, `goal-events.ts:540`). Этот блок идентичен от хода к ходу.
2. **Волатильные счетчики (`counters`)**: Точный расход токенов, активное время, счетчик запусков (`Autonomous runs: 3/20`).

### Сохранение префикса для неявного кэширования (`goal-live-retention.ts`)
У провайдеров вроде OpenAI Responses или DeepSeek кэшируется совпадающий префикс запроса от начала. Если просто дописывать блок цели в конец истории, то после ответа ассистента позиция этого блока смещается, и кэш срывается на каждом шаге.
- Класс `LiveTailRetention` внедряет временные сообщения с `role: "custom"`, `customType: "pi-goal-live-context"` (`goal-live-retention.ts:25-32`).
- Он запоминает индекс (`anchorIndex`) и SHA-256 хеш каждого сообщения истории. Ранее отправленные хвосты воспроизводятся **в тех же позициях истории**, где они находились в прошлых запросах (`goal-live-retention.ts:16-24`).
- Новые данные только дописываются в конец. Любая реальная перезапись истории (компенсация/сжатие, смена ветки) вызывает сброс (`liveRetention.clear()`).

### Управление явными точками кэша (`goal-prompt-cache.ts`)
Для провайдеров с явными маркерами кэширования (Anthropic Claude с `cache_control: { type: "ephemeral" }` или AWS Bedrock с `cachePoint`):
- Сам Pi по умолчанию устанавливает маркер кэширования на последнее пользовательское сообщение.
- Поскольку блок цели внедряется временно и не попадает в постоянную историю, установка маркера на него бесполезна.
- Функция `cacheGoalHistory` (`goal-prompt-cache.ts:17-68`) перехватывает исходящую структуру `payload.messages`, находит маркер на динамическом хвосте и **переносит его назад на последнее реальное историческое сообщение диалога** (пользователя, ассистента или результат вызова инструмента). Временный блок цели исключается из кэшируемого префикса.

### Сжатие сессии (*Session Compaction*, `goal-compaction.ts`)
При процедуре сжатия контекста в Pi:
- Все промежуточные маркеры чекпоинтов приводятся к ультракомпактному формату v2: `<pi_goal_continuation goal_id="..." kind="checkpoint" v="2"/>` (`goal-events.ts:43-55`, `goal-record.ts:74-82`).
- Формируется детерминированная сводка состояния цели и последних событий из журнала (`buildGoalCompactSummary`, `goal-compaction.ts:16-70`).
- На следующем ходе взводится флаг `isPostCompactReminderPending`, и в промпт внедряется дельта изменений, предотвращающая потерю нити рассуждений (`goal-events.ts:546`).

## 7. Жизненный цикл выполнения и точки контроля человека

### Стандартный цикл шага выполнения
```text
[ turn_start ]
  │  • scheduler.turn() — проверка прав на запуск
  │  • goalService.beginTurn() — открытие транзакционного буфера
  │  • accounting.beginAccounting() — старт таймера хода
  ▼
[ Выполнение хода моделью ]
  │  • Модель вызывает рабочие инструменты (read, write, bash)
  │  • Модель вызывает update_goal_task(start/complete)
  │  • tool_call interceptor:
  │      - блокирует работу после вызова stop-инструмента (post-stop guard)
  │      - блокирует работу, если чекпоинт устарел (stale checkpoint guard)
  ▼
[ turn_end / agent_settled ]
  │  • goalService.flushTurn():
  │      1. Захват блокировки .locks/<goal>.lock
  │      2. Проверка ревизии (optimistic concurrency)
  │      3. Атомарная запись активного/архивного файла
  │      4. Запись накопившихся событий в goal_events.jsonl
  │      5. Освобождение блокировки
  ▼
[ Планирование следующего шага ]
  │  • Если autoContinue включен и лимит maxAutonomousRuns не исчерпан:
  │      - при наличии полезной работы: немедленный kickoff следующего хода
  │      - при отсутствии работы и idleContinuationBackoff=true: экспоненциальная пауза (30с..300с)
```

### Завершение цели и независимый аудит (`goal-completion.ts`, `goal-auditor.ts`)
1. Модель вызывает `update_goal({ status: "complete", completion_summary: "..." })`.
2. **Проверка гейта задач**: Если в `taskList` установлен флаг `blockCompletion: true` и есть незавершенные задачи, операция немедленно отклоняется с ошибкой (`taskCompletionBlockWarning`, `goal-completion.ts:55`).
3. **Обход аудита**: Если аудитор отключен глобально (`settings.disabled = true`) или для данной цели (`skipAuditor = true`), цель завершается сразу с записью `audit_skipped` (`goal-completion.ts:68-73`).
4. **Запуск сессии аудитора** (`runGoalCompletionAuditor`, `goal-auditor.ts:270`):
   - Создается изолированная сессия агента Pi в оперативной памяти (`SessionManager.inMemory()`) с пустым набором расширений (`makeAuditorResourceLoader`, `goal-auditor.ts:220`).
   - Аудитор получает модель, настроенную в `/goal-settings` (по умолчанию модель текущей сессии).
   - Ему передаются: формулировка цели, контракт верификации, дерево задач и недоверенное заявление исполнителя.
   - Аудитор наделяется исключительно инструментами инспекции: `read`, `grep`, `find`, `ls`, `bash`. Инструменты модификации (`write`, `edit`) отсутствуют (`goal-auditor.ts:181`).
   - Аудитор обязан завершить свой отчет строгим маркером на последней строке: либо `<approved/>`, либо `<disapproved/>` (`goal-auditor.ts:60-65`).
5. **Обработка вердикта**:
   - При одобрении (`<approved/>`) цель помечается как `complete`, перемещается в `.pi/goals/archived/`, а сессионный фокус очищается (`goal-completion.ts:145-155`).
   - При отказе (`<disapproved/>`) цель остается в статусе `active`, замечания аудитора записываются в ledger и будут внедрены в промпт на следующем ходу (`[AUDITOR REJECTION]`).
   - **Ручное прерывание по Esc**: Если пользователь нажимает `Esc` во время аудита, открывается диалог `showEscapeDialog` (`goal-completion.ts:125-135`), где человек может выбрать: «Завершить без аудита» (*complete without audit*) или «Продолжить работу» (*continue working*).

### Механизм Blocker Oracle (`goal-oracle.ts`)
Если модель вызывает `update_goal({ status: "blocked", reason: "..." })`, рантайм не останавливает работу сразу, если включен Blocker Oracle:
- Вычисляется стабильный фингерпринт блокера (`buildBlockerFingerprint`, `goal-oracle.ts:44-55`) на основе хеша цели, контракта, формы дерева задач и нормализованной причины.
- Запускается отдельная сессия с более мощной моделью-оракулом (только инструменты `read`, `grep`, `find`, `ls` — без `bash` и без записи).
- Оракул выносит вердикт: `actionable` (предлагает конкретную альтернативу), `needs_human` или `insufficient_context` (`goal-oracle.ts:120-140`).
- Если найден путь решения (`actionable`), цель **остается активной**, совет оракула возвращается модели, и работа продолжается без привлечения человека.

## 8. Подсистемы надёжности и отказоустойчивости

В коде реализован широкий комплекс защитных механизмов против сбоев окружения, конкурентности и переполнения контекста:

1. **Восстановление хранилища (`goal-recovery.ts`)**:
   Команда `/goal-recovery` выполняет глубокое сканирование:
   - ищет непарсящиеся файлы `active_goal_*.md` (`scanMalformedGoalFiles`);
   - находит поврежденные строки в `goal_events.jsonl`;
   - выявляет «мертвые» lock-файлы от упавших процессов (`scanStaleLocks`);
   - находит рассинхронизацию кэша пула целей (`orphanedSnapshotGoals`).
   При вызове `/goal-recovery repair` перед любым изменением создается резервная копия в `.pi/goals/.recovery-backup/<timestamp>/` (`goal-recovery.ts:150-180`).
2. **Диагностика здоровья сессий (`goal-session-health.ts`)**:
   Защита от проблемы Issue #30. Исторически каждый чекпоинт автономного цикла сохранял в сессию полный промпт цели (~6.4 КБ), что приводило к лавинообразному росту файла сессии (сотни мегабайт). Модуль инспектирует JSONL сессии, вычисляет объем устаревших чекпоинтов и выводит рекомендации по использованию внешней утилиты восстановления `pi-goal-x-recover`.
3. **Безопасность сессий и изоляция воркеров (`goal-session-safety.ts`)**:
   - `isDelegatedGoalSession`: проверяет переменные `PI_SUBAGENT_CHILD` и `PI_SUBAGENT_DEPTH`. Если текущий агент запущен как сабагент, расширение полностью блокирует создание собственных целей и переключение фокуса, защищая состояние основной сессии.
   - `GoalAuditMessages`: буферизует сообщения аудита и сбрасывает их в диалог только тогда, когда сессия свободна (`ctx.isIdle()`) и контекст не устарел (`isStaleExtensionContextError`).
4. **Сетевой бэкофф (`network-error-backoff.ts`)**:
   При сбоях сетевого подключения к LLM-провайдеру во время автономного цикла включается ступенчатая лестница задержек: 5с → 10с → 20с → 40с → 80с (`NETWORK_ERROR_BACKOFF_DELAYS_MS`). Это защищает от мгновенного сжигания попыток и перегрузки API.
5. **Управление прерываниями (`goal-interruption.ts`)**:
   Поддерживает три стратегии реакции на прерывание по Esc/паузу (`pauseOrder`, `goal-interruption.ts:40-55`):
   - `together` (по умолчанию): одновременная пауза цели и немедленный `ctx.abort()` текущего хода;
   - `goal-first`: цель переводится в паузу, но текущему ходу модели дается завершиться;
   - `turn-first`: ход останавливается, но цель удерживается в активном состоянии (`held`), ожидая явного возобновления пользователем.
6. **Оптимистичная конкурентность планировщика (`goal-scheduler-state.ts`, `goal-scheduler.ts`)**:
   Каждая цель привязывается к сессии-владельцу (`owner: sessionId`). Если другая сессия пытается продолжить выполнение цели, планировщик требует явного выполнения `/goal-resume` для перехвата владения (`goal-scheduler.ts:48-52`).

## 9. Конфигурация, команды и горячие клавиши

### Иерархия настроек (`goal-settings.ts`)
Настройки читаются из трех уровней с приоритетом:
`Переменные окружения` → `Проект (.pi/pi-goal-x-settings.json)` → `Глобальные (~/.pi/agent/pi-goal-x-settings.json)` → `Дефолтные значения`.

#### Ключевые параметры конфигурации:
- `disableTasks` (boolean): полное отключение системы задач (оставляет только 3 базовых инструмента).
- `disableContracts` (boolean): отключение обязательных требований контрактов верификации.
- `subtaskDepth` (number, default: 1): максимальная глубина вложенности подзадач.
- `maxAutonomousRuns` (number): лимит автономных продолжений подряд (0 — отключить продолжения; не задано — бесконечно).
- `idleContinuationBackoff` (boolean): включение прогрессивной паузы (30с..300с) при отсутствии продуктивных действий.
- `strictExecutionContract` (boolean): требование явного вызова `update_goal` с `continuation: {kind: "ready"|"wait"}`.
- `provider`, `model`, `thinkingLevel`: модель и глубина рассуждений для completion auditor.
- `disabled` (boolean): полное отключение независимого аудитора.
- `auditorProjectResources` (boolean): разрешить ли аудитору загружать локальные скиллы проекта (по умолчанию `false` для изоляции).
- `pauseOrder` (`"together"` | `"goal-first"` | `"turn-first"`): поведение клавиши паузы.
- `goalsRoot` (string): кастомный абсолютный путь к каталогу хранения целей.
- `hideUnfocusedPrompt` (boolean): подавление напоминания `[PI GOAL UNFOCUSED]` в промпте модели при наличии открытых целей без фокуса.
- `hideUnfocusedBanner` (boolean): скрытие виджета невыбранной цели в TUI.
- `objectiveMaxChars` (number): ограничение длины текста цели.
- `stallTimeoutMinutes` (number): время неактивности до вывода предупреждения `[GOAL STALLED]`.

### Slash-команды (`goal-controls.ts:5-24`, `goal-commands.ts`)
Расширение регистрирует 16 команд действий (*Action IDs*), каждую из которых можно переименовать или дополнить алиасами в настройках:
1. `/goal [idea]` — запуск диалогового составления обычной цели.
2. `/sisyphus [idea]` — запуск составления упорядоченной цели Sisyphus.
3. `/goal-direct <objective>` — прямое мгновенное создание обычной цели.
4. `/sisyphus-direct <objective>` — прямое создание Sisyphus-цели.
5. `/goal-tweak <change>` — диалоговая корректировка цели, задач или бюджета.
6. `/goal-pause` — постановка активной цели на паузу.
7. `/goal-resume` — возобновление работы и обновление лимита автономных запусков.
8. `/goal-clear` — архивация сфокусированной цели (с подтверждением).
9. `/goal-list` — список всех открытых целей проекта с меткой фокуса.
10. `/goal-status [verbose|health]` — статус текущей цели / детальная диагностика.
11. `/goal-refresh` — принудительное перечитывание файлов с диска и сброс кэшей.
12. `/goal-recovery [repair]` — отчет о целостности данных / запуск восстановления.
13. `/goal-focus` — интерактивный выбор активной цели для текущей сессии.
14. `/goal-unfocus` — отключение фокуса текущей сессии от общей цели проекта.
15. `/goal-settings [controls]` — интерактивный редактор настроек и хоткеев.
16. `/goal-cancel` — отмена текущего неподтвержденного черновика цели.

### Горячие клавиши (`goal-controls.ts:35-70`)
- `Escape`: пауза выполнения / прерывание аудита / сворачивание дашборда.
- `Ctrl+Shift+T`: переключение виджета над редактором между компактным и развернутым режимом (*compact / expanded*).
- `Ctrl+Shift+A`: мгновенное включение/выключение аудитора для текущей цели (`skipAuditor`).
- `Ctrl+Shift+Up` / `Ctrl+Shift+Down`: скроллинг компактного списка задач в виджете.

## 10. Ограничения, подводные камни и детали реализации

При анализе исходного кода выявлен ряд важных архитектурных нюансов и потенциальных ловушек:

1. **Конфликты внешнего редактирования и сброс транзакций (`goal-service.ts:180-215`)**:
   Если во время выполнения хода файл цели был изменен извне (другим процессом, редактором или Git), транзакционный буфер `flushTurn` обнаруживает несовпадение поля `revision`. В этом случае все накопленные за ход локальные изменения задач **целиком отклоняются** (`Goal changed in another process; buffered changes were rejected`). Единственное, что спасается, — это дельта затраченных токенов и времени, которая аддитивно накладывается на свежую дисковую запись (`goal-service.ts:205-207`).
2. **Особенности кэширования пула целей NAF (`storage/goal-files.ts:45-75`)**:
   Для устранения задержек TUI при чтении файлов на каждом кадре реализован кэш директории `goalPoolCache` и снимок `.goals-pool-snapshot.json`. Кэш инвалидируется только при операциях самого расширения или изменении `mtime` директории. Если пользователь вручную изменил содержимое файла цели *на месте* без изменения `mtime` каталога, сессия может некоторое время видеть устаревшие данные до вызова `/goal-refresh`.
3. **Строгость конфигурации модели аудитора (`goal-auditor.ts:245-255`)**:
   Функция `resolveAuditorModel` категорически блокирует запуск при указании одного только провайдера без модели: конфигурация вроде `{ "provider": "anthropic" }` возвращает фатальную ошибку (`Provider-only auditor configuration is refused`). Требуется обязательно указывать явную пару `provider/model`.
4. **Sisyphus не имеет аппаратного счетчика (`docs/architecture.md:133`)**:
   Пользователь может ожидать, что режим Sisyphus жестко переключает шаги на уровне кода и не дает модели сделать шаг 2 раньше шага 1. В реальности это промпт-инструкция. Если модель самовольно нарушит порядок, рантайм технически не заблокирует вызов инструмента; нарушение сможет пресечь только completion auditor на этапе сдачи работы.
5. **Специфика блокировок на Windows (`storage/goal-lock.ts:40`, `storage/atomic-rename.ts:15`)**:
   Окна удержания блокировки минимизированы до миллисекунд (8 попыток по 1 мс). При высокой нагрузке на файловую систему в Windows вызов `acquireGoalLock` может завершиться ошибкой за ~10 мс. Модуль `atomic-rename.ts` вынужден использовать синхронные задержки через `Atomics.wait(SharedArrayBuffer)` для обхода системных блокировок Windows `EPERM`/`EBUSY`.
6. **Ограничение вложенности задач по умолчанию (`goal-task-tools.ts:98`)**:
   Значение `subtaskDepth` по умолчанию равно 1. Это означает, что задачи могут иметь дочерние подзадачи, но у подзадач не может быть своих детей (максимум 2 уровня иерархии). Попытка модели передать более глубокое дерево в `set_goal_tasks` вызовет ошибку валидации.
7. **История чекпоинтов в сессиях (`goal-session-health.ts:10-25`)**:
   Сессии, созданные до внедрения протокола чекпоинтов v2, хранят громоздкие блоки в `session.jsonl`. Расширение детектирует это через `/goal-status health`, но само файлы сессий Pi не модифицирует — для очистки требуется внешний запуск утилиты `scripts/recover-session-checkpoints.mjs`.
